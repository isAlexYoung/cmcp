# Linux 界面内更新

从 4.23.2 的正式 Linux 安装包开始，在「设置 → 关于」点击「检查更新」。发现新版本后点击「下载更新」，下载进度与校验状态会显示在页面和首页进度环；下载完成后按钮变成「安装更新」。只有再次点击并确认重启后才安装。

## 安装方式

从 Ubuntu 4.23.3 开始，更新检查会按 Linux x64 选择可用的最高稳定版本。Ubuntu 4.23.2 查询的是仓库级 Latest，因此从 4.23.2 升级到首个 Ubuntu 专版时，请从该版本发布页安装一次 `.deb`。这个安装包也会更新系统的应用菜单图标。

首次安装使用发布页的 `CMCP-<版本>-linux-x64.deb`。首次安装需要系统管理员权限，后续界面内更新不需要 sudo 密码，也不操作系统全局代理。

下载只接受官方 GitHub 稳定发布中的精确 Linux x64 更新 ZIP，核对发布的 `.sha256`、长度与 GitHub 资产摘要。更新 ZIP 与首次安装的 `.deb` 来自同一份源代码与文件清单。安装前再次核对 ZIP 摘要和包内全部文件摘要、平台、版本、Node ELF、文件路径及类型，拒绝额外文件、路径穿越和符号链接。

用户状态目录通常是 `~/.local/state/cmcp`，也支持 `CMCP_STATE_DIR`。更新包解压到该目录的 `updates/apps/app-<唯一标识>/`，通过原子替换 `updates/active.json` 切换当前版本。系统入口 `/usr/bin/cmcp` 和应用菜单先检查用户更新的完整性与版本，再决定启动用户更新还是 `/opt/cmcp` 系统版本。

这样既不需要提升界面程序权限，也不覆盖 `.deb` 的系统文件。`dpkg` 显示的是系统基础包版本，实际运行版本以 CMCP「关于」为准。如果以后通过 apt 安装了更新的基础包，启动器会优先使用版本更高的基础包。用户更新损坏时自动使用基础包。

## 重启与恢复

新包验证完成后，原窗口正常退出并清理连接和后台。安装器核对原进程的 PID 与启动时间，确认其退出后才激活新版本。新版本必须成功启动后台并显示首页，再返回对应更新请求的健康确认；未能启动或健康检查超时会终止失败实例、恢复原指针并重新打开旧版本。

失败不改写设备配置、界面设置、工具配置或密钥环密码。成功后删除已经验证的旧用户版本和本次下载 / 请求文件。系统基础包和其他用户文件不在清理范围内。更新会使当前连接暂时断开，重启后按原配置恢复。

4.23.2 之前本轮临时构建的 `4.23.2~ubuntu1` 测试包没有启动器，需要手动安装一次正式 `.deb`；从该正式包升级到后续版本即可全程使用界面。

## 发布与验证

统一发布工作流支持 `all / windows / macos / linux`。为已经发布的 4.23.2 追加 Linux 时只上传 Linux ZIP、DEB、对应 SHA256 和本次 Linux 源码快照 / SHA256，不改写既有 Windows / macOS 安装包、源码资产或版本标签。Linux 清单内记录实际构建提交，可与 `CMCP-4.23.2-linux-source.zip` 核对。

Linux CI 检查共享协议回归、Linux 文件 / 命令 / 进程、Python 安装器事务，以及实际 GTK 更新链路：下载完成、取消安装、确认安装、旧窗口退出、新窗口与后台健康确认、配置保留和退出清理。校验失败、额外文件、路径穿越、符号链接、旧进程未退出、启动失败恢复等由独立事务测试覆盖。原生双系统 GNOME / X11 的多屏、浏览器、密钥环解锁和真实云端连接仍需实机验收。
